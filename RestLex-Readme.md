# RestLex — руководство

RestLex — система резервного копирования на базе [restic](https://restic.net/). Состоит из трёх независимых программ, которые можно ставить по отдельности или все вместе:

| Файл | Что это | Обязателен? |
|---|---|---|
| `restlex-agent.exe` | Служба Windows, которая реально делает бэкапы по расписанию | Да, на каждой машине с бэкапами |
| `restlex.exe` | Графическая программа для настройки профилей бэкапа | Да, хотя бы раз — чтобы создать профили |
| `restlex-webserver.exe` | Веб-сайт со сводкой всех бэкапов со всех машин | Нет, опционально (удобно, если машин много) |

Ставится всё это одним файлом — **`RestLex-Setup.exe`** (см. раздел «Установка» ниже).

---

## 1. RestLex Agent (`restlex-agent.exe`)

Служба Windows **`RestlexAgent`** — работает в фоне без графического интерфейса, под системным пользователем, стартует автоматически с Windows.

Что делает:
- Хранит **профили** бэкапа (что копировать, куда, по какому расписанию, с каким паролем репозитория) в `C:\ProgramData\RestLex\profiles.json`.
- Сам, по расписанию, запускает `restic` и делает снапшот в репозиторий (локальная папка, сетевой путь, S3/B2/Azure и т.д. — что поддерживает restic).
- После каждого бэкапа, если настроен **Report URL**, отправляет POST-отчёт (успех/ошибка, сколько данных, сколько файлов) на веб-сервер отчётов.
- Поднимает локальный HTTP API на `127.0.0.1:17345` (только с этой же машины) — им пользуется GUI и, при желании, ваши собственные скрипты (см. `REST_API.md` в репозитории — там пошагово расписано, как запустить бэкап по API).
- Есть watchdog: если служба падает — Планировщик заданий поднимает её обратно.

**Доступ к API закрыт токеном.** Все запросы, кроме проверки живости `GET /health`, требуют заголовок `Authorization: Bearer <api_token>`. Токен агент **генерирует сам** при первом старте службы и сохраняет в `C:\ProgramData\RestLex\config.json` (поле `api_token`) — вручную его задавать не нужно; оттуда его читают GUI, CLI и внешние интеграции. Если включено шифрование секретов, значение лежит в виде `enc:` (DPAPI, привязка к машине).

**Права на `C:\ProgramData\RestLex\`:** полный доступ — только у SYSTEM и администраторов, у обычных пользователей — чтение и запуск, а `config.json` и `profiles.json` закрыты от них полностью. Служба работает под SYSTEM и запускает отсюда программы, поэтому право записи для пользователей означало бы повышение привилегий. Если каталог восстанавливается из бэкапа вручную — права нужно вернуть такими же.

**Самообновление службы.** Перед подменой своего бинарника агент проверяет Authenticode-подпись скачанного файла и допускает только наш EV-сертификат (список разрешённых подписантов зашит в агенте — новый серийник добавляется в него заранее, до перевыпуска сертификата). Логика трёхзначная: подпись валидна — ставим; подпись явно испорчена или подписант чужой — отказ; **проверить не удалось** (PowerShell не запустился или не уложился в 10 секунд) — пишем ошибку в лог и всё равно ставим. Последнее — сознательный компромисс: иначе одна сломанная машина (и весь парк Win7/2008R2) навсегда остались бы без обновлений.

Если новая версия не поднялась, `self_update.bat` откатывается на `restlex-agent.exe.bak`. Резервная копия **не удаляется по таймеру**, а живёт до следующего успешного обновления. Повторная установка той же версии блокируется маркером неудачи; кнопка «Проверить и обновить» снимает этот маркер, но не чаще раза в 6 часов на одну версию — чтобы не получился бесконечный цикл «подмена → падение → откат».

**Битые конфиги не приводят к потере данных:** если `config.json` или `profiles.json` не читается (обрыв записи, порча), файл уводится в `<имя>.bad-<дата>` и создаётся новый; профили, которые не удалось разобрать, остаются в файле как есть, а не пропадают, и одна испорченная запись больше не уносит с собой остальные профили.

Управление из командной строки (обычно этим занимается установщик, вручную нужно редко):
```
restlex-agent.exe install     — зарегистрировать и запустить службу
restlex-agent.exe uninstall   — удалить службу
restlex-agent.exe start/stop  — запустить/остановить
restlex-agent.exe status      — текущее состояние
```

Все данные агента — в `C:\ProgramData\RestLex\` (профили, конфиг, логи в подпапке `logs\`).

## 2. RestLex GUI (`restlex.exe`)

Обычное окно Windows, с которым работает человек. Через него:

- Создаются и редактируются **профили бэкапа**: что копировать (папки/диски), куда (репозиторий restic — локально, сетевой диск, облако), пароль репозитория, расписание, глубина хранения версий.
- Можно вручную запустить бэкап или восстановление (`restic restore`) из любого снапшота.
- Смотрите статус службы агента, логи, историю запусков.
- Настраивается **Report URL** (вкладка «Веб-сервер») — адрес, куда агент шлёт отчёты о бэкапах (см. раздел 3).
- Есть настройки Telegram-уведомлений, автообновления и т.д.

Запуск бэкапа из командной строки — `restlex.exe --run-backup <pid>` (и `--no-scan` при необходимости): GUI открывается и сразу стартует указанный профиль. Раньше флаг молча игнорировался и просто открывалось окно.

GUI **не обязан быть постоянно открытым** — он нужен только чтобы настроить профили. Сами бэкапы делает служба агента в фоне, даже если GUI закрыт или пользователь вышел из системы.

Запускается ярлыком с рабочего стола (создаётся установщиком) или напрямую `C:\ProgramData\RestLex\restlex.exe`. Требует прав администратора (управляет службой Windows).

### Восстановление файлов — два способа

Во вкладке «Восстановление» есть дерево снапшотов репозитория и два принципиально разных способа получить файлы обратно:

**1. Обычное восстановление (через restic)** — как в классическом бэкапе:
- **«Восстановить по месту хранения»** — вернуть выбранные файлы/папки туда, откуда они бэкапились (перезапишет текущие версии).
- **«Восстановить выбранное»** — распаковать выбранное в отдельную папку (например, на рабочий стол), не трогая оригинал.
- Под капотом — обычный `restic restore`, физически копирует файлы из репозитория на диск. Годится для полного восстановления после сбоя/переноса на новую машину.

**2. Mount снапшота как сетевая папка (WebDAV), без восстановления** — если нужно быстро посмотреть/скопировать 1-2 файла, необязательно ждать полного восстановления:
- Кнопка **«Подключить»** в блоке «Mount в Explorer (WebDAV)» — служба агента поднимает read-only WebDAV-точку для выбранного снапшота.
- Кнопка **«Открыть»** — Windows Explorer открывает её как обычную сетевую папку (путь всегда вида `\\localhost@порт\DavWWWRoot`) — снапшот виден и листается как обычная папка с файлами, можно перетаскивать файлы наружу мышкой, ничего заранее не распаковывая на диск.
- Точка монтирования поднимается **только на `127.0.0.1`** и доступна только с этой машины: с другого компьютера в сети её не видно и подключить нельзя. Логин/пароль при подключении не спрашиваются и не нужны (подробности — `WINDOWS-MOUNT.md`).
- WinFsp или сторонние драйверы не нужны — используется встроенный в Windows клиент WebDAV (служба `WebClient`). Если она выключена (бывает на Windows Server), GUI сам предложит включить её через DISM и попросит перезагрузку.
- Кнопка **«Отключить»** — отмонтировать, когда закончили.

Разница простыми словами: способ 1 — «скопировать файлы из бэкапа на диск», способ 2 — «открыть бэкап как флешку, посмотреть и забрать нужное, ничего не копируя целиком».

## 3. Веб-сервер отчётов (`restlex-webserver.exe`)

Отдельная служба Windows **`RestlexWebServer`** — если бэкапится много машин, удобно смотреть все отчёты в одном месте через браузер, а не заходить на каждую машину по отдельности.

Слушает **два порта** (обязательно разные, конфигурируются при установке):

| Порт (по умолчанию) | Что | Кто стучится |
|---|---|---|
| **8798** | Веб-интерфейс: таблица бэкапов, история, настройки, вход по логину/паролю | Браузер человека |
| **8797** | Только приём отчётов `POST /report` | Агенты (`restlex-agent`) с других машин |

Разделение портов сделано специально: порт `8797` можно закрыть от интернета фаерволом, оставив открытым только для бэкапящихся машин внутри сети, а `8798` — для просмотра людьми.

Что видно в веб-интерфейсе:
- Таблица всех профилей со всех машин: статус (успех/ошибка), время, объём, сколько файлов изменилось, «свежесть» (не просрочен ли бэкап).
- История по каждому профилю.
- Админ-панель: пользователи, группы машин, Telegram-уведомления об ошибках, порог «просрочен».
- Открытые страницы обновляются автоматически для всех пользователей: новые отчёты, история, группы, настройки и журнал обновлений появляются без ручной перезагрузки. Сервер рассылает изменения через SSE; при разрыве соединения браузер повторяет проверку каждые 15 секунд.
- При полной перезагрузке страницы (например, F5) сверху на короткое время показывается полоса загрузки.
- На главной странице открывается история профиля кнопкой «История». Внутри истории администратор может удалить все отчёты этого профиля кнопкой «🗑 Удалить всё». Удаление требует подтверждения и не удаляет настройки профиля на агенте.
- Верхняя шапка разделена на название, версии Launcher/Service/Web, действия и фильтры. Фильтры показывают все отчёты, проблемные, ошибки, просроченные, десять самых старых или профили без группы. Выбранный фильтр сохраняется при обновлении страницы. Рядом со счётчиком «Показано» выводится время последнего успешного обновления панели.
- Организации сворачиваются по заголовку; общая кнопка в полосе фильтров сворачивает или разворачивает все группы. Заголовок проблемной группы подсвечивается и показывает число проблем, даже когда таблица свёрнута. Состояние групп хранится на сервере отдельно для каждого пользователя и сохраняется после выхода и повторного входа.
- Счётчик ошибок обновлений в шапке показывает только новые ошибки для текущего пользователя и сбрасывается после открытия журнала «Обновления»; у других пользователей счётчик не меняется.
- В шапке можно выбрать светлую или графитовую тему. Выбор хранится отдельно для каждого пользователя и сохраняется после перезагрузки страницы и повторного входа.
- Вход сохраняется при перезапуске веб-сервера и продлевается при работе со страницей. Срок бездействия настроен на 30 дней, но действует более строгий абсолютный предел — 7 суток с момента входа. Выход или отзыв доступа администратором также завершает сессию; в базе хранится только хеш токена.
- Журнал «История обновлений» при открытии показывает только ошибки. Фильтры в верхней шапке переключают на все записи или только успешные; блок заблокированных обновлений фильтр не скрывает.

Обязательные параметры при установке — **пароль администратора** (логин `admin`) и **API-ключ** (им агенты подтверждают, что имеют право слать отчёты). Через установщик (`RestLex-Setup.exe`) API-ключ генерируется автоматически и сохраняется в `api-key.txt` рядом с программой — оттуда его нужно взять и прописать агентам, которые должны отчитываться этому серверу.

При пустом или нерасшифрованном пароле администратора новый веб-сервер не создаёт учётную запись с паролем по умолчанию. Для баз, созданных прежними версиями, проверьте и смените старые учётные данные перед публикацией сервера.

Данные веб-сервера — `C:\ProgramData\RestLex\webserver-config.json` (настройки), `webserver.db` (история отчётов, SQLite) и `webserver.sessions.db` (действующие веб-сессии; рядом с `webserver.db`).

### Секреты веб-сервера и восстановление доступа

- Секреты в `webserver-config.json` (`admin_password`, `viewer_password`, `api_key`, `tg_token`) хранятся **зашифрованными всегда** — префикс `enc:`, DPAPI с привязкой к машине. Тумблер «Шифровать секреты» в GUI на этот файл не влияет: и служба, и GUI пишут его в `enc:` безусловно. Старые плейнтекстовые конфиги читаются по-прежнему и перешифровываются при первом сохранении.
- **Секреты агента и профилей — это отдельная история.** В `config.json` (`tg_token`, `api_token`, `report_api_key`, `update_api_key`) и `profiles.json` (`repo_password`) шифрование **опционально**: оно включается тумблером «Шифровать секреты» в настройках GUI и **по умолчанию выключено** — то есть эти значения по умолчанию лежат на диске плейнтекстом. Всё, что ниже написано про «переезд на другое железо» и про откат версии, относится именно к веб-серверу.
- Пароли пользователей в базе хранятся как **PBKDF2-HMAC-SHA256, 200 000 итераций** (`pbkdf2:<итерации>:<соль>:<хеш>`). Записи старого формата `sha256:соль:хеш` принимаются и автоматически пересчитываются при первом успешном входе — пользователям ничего делать не нужно.
- Сессия в веб-интерфейсе продлевается при каждом обращении, но не дольше **7 суток с момента входа**. Этот предел действует и для активного дашборда: после него нужен повторный вход. Смена пароля пользователя, смена его роли и удаление гасят его сессии. Все формы админки защищены CSRF-токеном.
- Форма входа считает пароль (PBKDF2, 200 000 итераций) не более чем в 3 потока одновременно; лишние попытки получают `429` **без** запуска проверки — чтобы поток неаутентифицированных POST не забивал CPU сервера.

**Если конфиг переехал на другое железо** (восстановление ProgramData из бэкапа, переустановка ОС, перенос сервера) — DPAPI-ключ привязан к машине, и `enc:`-значения перестают расшифровываться: вход по конфигу закрыт, порт приёма отчётов отвечает `503`. В лог и в консоль пишется явное сообщение с причиной. Лечится без переустановки — задать нужные секреты заново, не трогая остальной конфиг:

```
restlex-webserver.exe stop
restlex-webserver.exe set-secret --name admin_password  --stdin
restlex-webserver.exe set-secret --name api_key         --stdin
restlex-webserver.exe set-secret --name viewer_password --stdin
restlex-webserver.exe set-secret --name tg_token        --stdin
restlex-webserver.exe start
```

С `--stdin` (или `--value -`) значение читается из стандартного ввода — аргумент `--value СЕКРЕТ` тоже работает, но виден в списке процессов, поэтому годится только для не очень чувствительных значений.

> **Службу нужно остановить до правки.** Запущенная служба держит конфиг в памяти и при первом же сохранении настроек в веб-админке перезаписывает файл целиком — свежий секрет с диска молча откатится. Команда об этом предупреждает в выводе.

> Если `webserver-config.json` повреждён и не разбирается как JSON, `set-secret` **отказывается работать** (сообщение + код возврата 2), а не пишет поверх него дефолты: иначе порт, `tg_chat` и настройки локаута обнулились бы ровно в том сценарии, ради которого команда и делалась.

Раньше единственным выходом был повторный `install`, затирающий весь конфиг.

> ⚠️ **Откат веб-сервера на предыдущую версию после обновления невозможен без ручных действий.** Старая сборка не понимает ни `enc:`-секреты в конфиге, ни PBKDF2-хеши паролей: после отката вход не сработает и агенты получат отказ. **Перед обновлением снимите копию `webserver-config.json` в плейнтексте и копию `webserver.db`** — только из них можно вернуться назад.

### Чтобы агенты реально начали слать отчёты — ключ нужен на ОБЕИХ сторонах

Одного факта, что веб-сервер установлен, недостаточно — отчёты не появятся, пока ключ не совпадает на клиенте и на сервере:

1. **На сервере**: ключ задаётся один раз при установке (`--api-key ...` или автогенерация в установщике, файл `api-key.txt`). Поменять его потом можно во вкладке «WEB → Веб сервер отчётов» в GUI (если GUI установлен и на этой же машине) — там есть поле **«API ключ:»**, при сохранении настроек можно сгенерировать новый.
2. **На каждом клиенте** (в GUI, вкладка «WEB → Веб сервер отчётов»): указать тот же **Report URL** и **точно тот же API-ключ** в поле «API ключ:» рядом с ним. Если ключи не совпадают, агент получит `401 Unauthorized` и отчёт не запишется в базу (в веб-интерфейсе просто ничего не появится — без явной ошибки на стороне сервера).
3. Проверить можно кнопкой рядом с полем (в GUI это «Проверить соединение») — она бьёт по Report URL с указанным ключом и явно скажет, верный ключ или нет.

## 4. Сервер обновлений (`restlex-update-server.exe`)

Отдельная служба, не входит в `RestLex-Setup.exe` и нужна только там, где парк машин обновляется централизованно: она раздаёт агентам новые `restlex-agent.exe` / `restlex.exe` из указанной папки, а те сами скачивают и ставят обновление.

```
restlex-update-server.exe install --port 8901 --folder C:\updates --api-key СЕКРЕТ
```

Что стоит знать при эксплуатации:

- **Ротация API-ключа без простоя**: `--api-key "старый,новый"` — принимаются оба, пока весь парк не подтянет новый. Ключ, в котором сама есть запятая, задаётся повторением флага: `--api-key A --api-key B` (тогда разбиения по запятой не происходит).
- Раздаются файлы из манифеста (`*.exe`) плюс белый список не-exe: `restlex-config.json` и `versions.json` — их тянут инсталляторы.
- Манифест (имена, размеры, SHA-256) кешируется и пересчитывается, только когда меняется состав, размер или время правки файлов в папке, включая `versions.json` / `version.txt`. Раньше каждый запрос читал все exe целиком в память — парк агентов клал сервер.
- Файлы отдаются потоком, число одновременных отдач ограничено (`max_concurrent_downloads` в конфиге, по умолчанию 32). Если очередь переполнена, клиент ждёт до 60 секунд и получает `503` — это заведомо раньше, чем истечёт его собственный 5-минутный таймаут.

## Установка — `RestLex-Setup.exe`

Один установщик на все три программы, с выбором, что ставить:

1. Запускаете от имени администратора (сам запросит права).
2. Выбираете компоненты:
   - **RestLex** — агент + GUI. Ставится почти всегда.
   - **Веб-сервер отчётов** — только если эта машина будет центральным сервером отчётов.
3. Если выбрали «Веб-сервер отчётов» — попросит придумать пароль администратора (логин `admin` фиксирован). API-ключ сгенерируется сам.
4. Выбираете, куда положить ярлык RestLex: себе на рабочий стол, всем пользователям компьютера или не создавать.
5. Установщик сам зарегистрирует нужные службы Windows и запустит их.

Повторный запуск установщика **переустанавливает** выбранное заново (файлы перезаписываются). Для веб-сервера это значит новый пароль/API-ключ — если сервер уже настроен и к нему привязаны агенты, переустанавливать его без необходимости не стоит (старый API-ключ у уже настроенных агентов перестанет подходить).

### Скачать и запустить установщик с сервера обновлений одной командой

`RestLex-Setup.exe` раздаётся сервером обновлений (`restlex-update-server`, порт по умолчанию `8901`) по ключу в заголовке `X-Api-Key`. Ниже `<SERVER>` — адрес сервера обновлений, `<API-KEY>` — его API-ключ (реальный ключ в инструкции/чаты не публиковать). Файл сохраняется в `%TEMP%`: текущая папка может быть `C:\Windows\System32` или недоступна для записи. Установщик сам запросит права администратора.

**CMD** (Windows 10 1803+ / Server 2019+, где есть встроенный `curl`), одна строка:

```
where curl >nul 2>&1 && (del /q "%TEMP%\RestLex-Setup.exe" 2>nul & curl -fsSL --fail -H "X-Api-Key: <API-KEY>" -o "%TEMP%\RestLex-Setup.exe" "http://<SERVER>:8901/api/download?file=RestLex-Setup.exe" && start "" "%TEMP%\RestLex-Setup.exe" || echo ERROR: download failed - check server address, API key and network) || echo ERROR: curl not found - use the PowerShell command below
```

- `-fsSL --fail` — при HTTP 401/404/503 curl завершится с ошибкой и не сохранит страницу ошибки под именем exe; установщик запускается только при успешной загрузке (`&&`).
- **Символ `%` в ключе.** В интерактивном окне CMD команду можно вставлять как есть (одиночный `%` не трогается; исключение — если в ключе встретится `%ИМЯ%` существующей переменной окружения, тогда надёжнее PowerShell-вариант). **В `.bat`/`.cmd`-файле каждый `%` в ключе нужно удвоить: `%%`** — иначе CMD съест его как начало переменной и сервер вернёт 401. `%TEMP%` в файле при этом остаётся как есть.

**PowerShell** (PowerShell 3.0+; на Win7/2008R2 без WMF 3.0+ и .NET 4.5 команда не сработает — там ставить установщик вручную):

```
$ErrorActionPreference='Stop'; [Net.ServicePointManager]::SecurityProtocol=[Net.ServicePointManager]::SecurityProtocol -bor [Net.SecurityProtocolType]::Tls12; $f=Join-Path $env:TEMP 'RestLex-Setup.exe'; try { Remove-Item $f -Force -ErrorAction SilentlyContinue; Invoke-WebRequest -UseBasicParsing -Headers @{'X-Api-Key'='<API-KEY>'} -Uri 'http://<SERVER>:8901/api/download?file=RestLex-Setup.exe' -OutFile $f; Start-Process $f } catch { Remove-Item $f -Force -ErrorAction SilentlyContinue; Write-Host ('ERROR: download failed: ' + $_.Exception.Message) -ForegroundColor Red }
```

Ключ в PowerShell стоит в одинарных кавычках — `%` и `$` в нём экранировать не нужно (только `'` пришлось бы удвоить).

## Минимальная установка: сервер + один клиент

Сценарий: одна машина — центральный сервер отчётов, вторая (или несколько) — машины, которые бэкапятся и отчитываются на сервер.

### Шаг 1 — машина-сервер

1. Запустить `RestLex-Setup.exe` от администратора.
2. Оставить галочку **«Веб-сервер отчётов»** (RestLex/агент на сервере ставить не обязательно, если он сам ничего не бэкапит — но можно оставить и его, не помешает).
3. Задать пароль администратора веб-интерфейса.
4. После установки открыть `C:\ProgramData\RestLex\api-key.txt` — скопировать API-ключ, он понадобится клиентам.
5. Узнать IP-адрес этой машины в локальной сети (`ipconfig`).
6. Проверить, что открывается `http://<IP-сервера>:8798` в браузере (страница входа) — значит служба поднялась.

### Шаг 2 — машина-клиент (та, что бэкапится)

1. Запустить `RestLex-Setup.exe` от администратора, оставить галочку **«RestLex»** (агент + GUI), веб-сервер не ставить.
2. Открыть GUI (ярлык на рабочем столе), создать профиль бэкапа: что копировать, куда (репозиторий), пароль, расписание.
3. Перейти во вкладку **«Веб-сервер»** и указать **Report URL**: `http://<IP-сервера>:8797/report` (порт `8797` — приём отчётов, не `8798`!).
4. Там же, если поле требует API-ключ — вставить ключ из `api-key.txt` с сервера.
5. Запустить бэкап (вручную кнопкой или дождаться расписания).

### Проверка

Открыть `http://<IP-сервера>:8798` в браузере на любой машине в сети, залогиниться как `admin` — в таблице должна появиться строка с профилем и хостом клиентской машины. Повторить шаг 2 для остальных клиентских машин, указывая тот же Report URL.

## Сборка из исходников

Нужны: Rust (stable; для агента под Win7 — nightly + `build-std`, см. `build.ps1`), Python 3.14 + PyInstaller + PyQt5 (GUI).

```
cd rust
cargo build --release -p restlex-webserver       # веб-сервер отчётов
cargo build --release -p restlex-update-server   # свой сервер обновлений (по желанию)
cargo build --release -p restlex-agent           # агент (для Win10+; Win7 — через build.ps1)
cd ..
pyinstaller restlex.spec --noconfirm             # GUI -> dist\restlex.exe
```

Или всё сразу: `pwsh ./build.ps1 -Components gui,agent,webserver,update-server`.

Установка собранного веб-сервера на свою машину-сервер:

```
restlex-webserver.exe install --api-key <ключ-для-агентов> --admin-password <пароль-веб-админа>
```

Ключи в исходниках не хранятся. Собственная сборка установщиков со вшитыми настройками организации
берёт их из `%USERPROFILE%\.restlex\build-secrets.json` (`update_key`, `install_key`; подпись — `sign_url`, `sign_token`).
Без этого файла собирается обычная публичная версия без ключей.

Обновления: по умолчанию программа обновляется с общего сервера `http://1221.by:3266` — он отдаёт только
подписанные exe, агент ставит обновление лишь при валидной подписи издателя. Свой сервер — `restlex-update-server`
и поле «Сервер обновлений» в настройках.

Форк со своей подписью: агент ставит обновления только от издателя из `ALLOWED_SIGNER_SERIALS`
(`rust/crates/restlex-agent/src/updater.rs`). Для собственного сервера обновлений впишите туда SERIALNUMBER
своего сертификата — неподписанные сборки агент не установит (fail-closed).
